# 实时语音转写工具 —— 整体设计方案（前半段：转写 → 聚合 → 送后端）

> 范围：本方案只覆盖「点击收音 → 实时转写 → 内容聚合 → 成批送到分析后端」。
> 分析后端（后半段）暂不实现，用**占位接口**对接，后续替换。
>
> 技术栈：**React 前端** + **Spring Boot(Java) ASR 代理** + DashScope FUN-ASR 实时转写。

---

## 1. 为什么必须有一层 Java 代理（关键结论）

阿里百炼 FUN-ASR 实时转写走 WebSocket，鉴权方式是请求头 `Authorization: bearer <DASHSCOPE_API_KEY>`。

- 浏览器原生 `WebSocket` **无法自定义请求头**，没法直接带 Key；
- 即使能带，把 API Key 放进前端 = **密钥泄露**，任何人可盗用刷量；
- 实时音频还需要服务端做**会话生命周期管理、重连、聚合、限流**，这些放浏览器都不稳定。

> 结论：前端只连**我们自己的 Java 代理**，由代理去连 DashScope。代理是「前半段」的核心，承担三件事：① 音频中继；② DashScope 会话管理；③ 内容聚合与投递分析后端。

## 2. 总体架构

```
┌─────────────────────────┐        ┌──────────────────────────────────────┐        ┌──────────────────┐
│        浏览器 (React)     │        │         Java 代理 (Spring Boot)         │        │   阿里百炼 DashScope │
│                          │  WS    │                                        │  WSS   │   FUN-ASR 实时转写   │
│  麦克风采集               │ ─────► │  /ws/asr  入站端点                      │ ─────► │  fun-asr-realtime    │
│  AudioWorklet            │ 音频   │   ├─ DashScope 会话管理 (run/finish)     │ 音频帧  │                      │
│   → 16k/16bit/单声道 PCM  │ 二进制 │   ├─ 结果回传 (result-generated → 前端)  │ ◄───── │  task-started        │
│  WebSocket 客户端         │ ◄───── │   └─ Aggregator 聚合器 (可配置触发)      │ 结果   │  result-generated    │
│  转写显示 / 状态机         │ 结果   │            │                           │        │  task-finished       │
└─────────────────────────┘        │            ▼  达到触发条件成批 POST       │        └──────────────────┘
                                    │      ┌───────────────────────┐          │
                                    │      │  分析后端 (占位 /mock)   │ ◄── HTTP │
                                    │      └───────────────────────┘   POST   │
                                    └──────────────────────────────────────┘
```

**职责切分**
| 组件 | 职责 |
|---|---|
| React 前端 | 采集麦克风、重采样为 16k PCM、收发 WS、显示实时/最终文本、收音状态机 |
| Java 代理 `/ws/asr` | 接前端音频 → 转发 DashScope；接 DashScope 结果 → 回前端显示 + 喂给聚合器 |
| Aggregator 聚合器 | 按可配置规则攒「最终句」，达到阈值成批投递分析后端，保证内容完整 |
| 分析后端（占位） | 接收成批文本做后续分析。当前仅 mock，约定好契约即可替换 |

> **设计取舍：聚合放在 Java 代理，而不是前端。** 原因：服务端到服务端投递更稳（无 CORS、无刷新丢数据、断网可本地排队重试），阈值集中配置，且天然能拿到 `sentence_end` 句界做完整切分。前端只负责展示与控制。

## 3. 端到端时序

```
用户点「收音」
  │
  ├─ 前端 getUserMedia → AudioWorklet 出 16k PCM → 连 ws://代理/ws/asr
  │
  ├─ 代理收到「开始」→ 连 DashScope → 发 run-task ──► 等 task-started
  │
  ├─ 前端持续推音频帧(每~100ms) ──代理透传──► DashScope
  │                                              │
  │                          DashScope 持续回 result-generated
  │        ┌─────────────────────────────────────┘
  │        ▼
  │   代理：① 原样回传前端(实时显示，含中间结果)
  │        ② sentence_end=true 的句子 → 投入 Aggregator
  │                                          │
  │                              触发器命中(字数/时间/停顿/最大延迟)
  │                                          ▼
  │                              成批 POST → 分析后端(占位)
  │
用户点「停止」
  │
  ├─ 前端发「结束」→ 代理发 finish-task ──► 等 task-finished
  │
  └─ 代理：强制 flush 聚合器残余内容 → 最后一批 POST → 关闭
```

## 4. 前端设计（React）

### 4.1 音频采集 —— 必须重采样为 16k PCM
浏览器麦克风默认 44.1k/48k，`MediaRecorder` 只能出 webm/opus，**不是裸 PCM**。
方案：`getUserMedia` → `AudioContext` → **AudioWorklet**（不用废弃的 ScriptProcessor）→ 在 worklet 里：
1. 取 Float32 采样；
2. 线性/抽取重采样到 16kHz；
3. Float32 → Int16（小端）；
4. 累积成 ~100ms 一帧（16000×0.1×2 = 3200 字节）通过 `port` 回主线程；
5. 主线程经 WebSocket 以 **二进制帧** 发给代理。

> 帧大小 100ms 是延迟与吞吐的平衡点，可配置（`frameMs`）。

### 4.2 收音状态机
`idle → requesting-mic → connecting → recording → stopping → idle`
任一环节出错 → `error`，自动回 `idle` 并提示。UI 在 `recording` 时显示实时文本（中间结果灰色、`sentence_end` 后转黑固化）。

### 4.3 与代理的消息协议（前端 ↔ 代理）
- 前端 → 代理：
  - 控制：JSON 文本 `{"type":"start","sessionId":"...","config":{...}}` / `{"type":"stop"}`
  - 音频：二进制帧（Int16 PCM）
- 代理 → 前端：JSON 文本
  - `{"type":"ready"}` 代理与 DashScope 就绪
  - `{"type":"partial","text":"...","beginTime":..,"endTime":..}` 中间结果（实时刷新当前句）
  - `{"type":"final","text":"...","sentenceId":n}` 固化的最终句
  - `{"type":"flushed","batchId":"...","chars":N}` 已成批投递后端（前端可做进度提示）
  - `{"type":"error","code":"...","message":"..."}`

### 4.4 封装为 Hook
`useAsrRecorder(config)` 返回 `{ status, partialText, finalSentences, start(), stop() }`，组件层只管渲染与按钮。

## 5. Java 代理设计（Spring Boot）

### 5.1 入站 WebSocket 端点 `/ws/asr`
用 `spring-boot-starter-websocket`，每个前端连接对应一个 `AsrSession`：
- 持有一条到 DashScope 的出站 WS（Java 11 `HttpClient` 或 OkHttp / `tyrus` 客户端）；
- 持有一个 `Aggregator` 实例；
- 维护 `task_id`、状态、心跳。

### 5.2 DashScope FUN-ASR 协议封装（已核实）
端点：`wss://dashscope.aliyuncs.com/api-ws/v1/inference/`（北京）/ `dashscope-intl...`（新加坡）
请求头：`Authorization: bearer ${DASHSCOPE_API_KEY}`

**run-task（文本帧，建立任务）**
```json
{
  "header": { "action": "run-task", "task_id": "<32位随机id>", "streaming": "duplex" },
  "payload": {
    "task_group": "audio", "task": "asr", "function": "recognition",
    "model": "fun-asr-realtime",
    "parameters": {
      "format": "pcm", "sample_rate": 16000,
      "max_sentence_silence": 800,            // VAD 断句静音阈值(ms)，越大越不容易把长句切碎
      "punctuation_prediction_enabled": true,  // 自动加标点
      "heartbeat": true                        // 静音期保活
      // "vocabulary_id": "<热词表id>"           // 可选：专业术语/人名提升准确率
    },
    "input": {}
  }
}
```
**task-started（事件）** → 收到后才能推音频。
**音频帧** → 二进制透传 DashScope。
**result-generated（事件，结果）**
```json
{
  "header": { "task_id": "...", "event": "result-generated" },
  "payload": { "output": { "sentence": {
    "begin_time": 0, "end_time": 2340,
    "text": "今天天气怎么样",
    "sentence_end": true,
    "words": [ { "begin_time":0,"end_time":300,"text":"今" } ]
  } } } }
```
> `sentence_end=false` 是**中间结果**（同一句会不断刷新/纠正）；`true` 表示该句**定稿**。这是保证内容完整、不切半句的关键。
**finish-task（文本帧）** → 收尾；**task-finished / task-failed（事件）** → 结束/错误（`header.error_code`）。

### 5.3 字段映射
- DashScope `result-generated` → 前端 `partial`/`final`；
- `sentence_end=true` 的 `text` → 同时投入 `Aggregator`。

## 6. 聚合 / 触发策略（核心，全可配置）

聚合器维护一个**最终句缓冲区** `List<Sentence>`，按下列触发器决定何时打包 POST。**所有切批都对齐句界（只收 `sentence_end` 的句子），从根上保证「不切半句、内容完整」。**

### 6.1 触发器（任一命中即 flush，可独立开关）
| 触发器 | 配置项 | 说明 |
|---|---|---|
| 字数阈值 | `charThreshold`(默认 200) | 缓冲累计字数 ≥ 阈值即打包。主要的「攒够数量」手段 |
| 时间间隔 | `intervalMs`(默认 8000) | 距上次 flush 超过该时间且缓冲非空即打包，避免说太久不上报 |
| 停顿断点 | `silenceFlushMs`(默认 1500) | 检测到一段说话停顿（两句间隔或无新句）→ 在自然语义边界打包，内容更完整连贯 |
| 句数阈值 | `sentenceThreshold`(默认 0=关) | 攒满 N 句即打包 |
| 最大延迟兜底 | `maxBufferMs`(默认 15000) | 强制上限，无论如何不让内容滞留过久 |
| 结束强制 | （内建） | `stop`/会话结束时把残余全部 flush，**绝不丢尾巴** |

### 6.2 保证「足够多且完整」的补充机制
1. **句界对齐切批**：只把 `sentence_end=true` 的句子计入并切批，中间结果永不入批 → 不会出现半句。
2. **上下文重叠（overlap）**：每批携带上一批末尾 `overlapSentences`(默认 1~2 句) 作为 `context`，分析后端能拿到跨批上下文，避免边界语义断裂。批正文与上下文分字段，下游可去重。
3. **最小批保护**：`minCharsToFlush`(默认 10)，时间/停顿触发时若内容太少则继续攒，避免碎批。
4. **批序号与会话关联**：每批带 `sessionId + batchSeq`（单调递增）+ `batchId`(uuid)，下游可重排、去重、判断是否最后一批(`isFinal`)。
5. **结束兜底 + 看门狗**：`stop`、前端断连、DashScope 异常关闭，三种路径都触发强制 flush；另有定时看门狗防止「缓冲有内容但触发器恰好都没命中」。

### 6.3 聚合实现要点
- 单线程/串行处理同一会话的结果（避免并发乱序）；
- 触发判断在每次收到 `final` 句后 + 一个周期性 `ScheduledExecutor`（驱动时间/停顿/兜底触发）；
- flush = 取出缓冲 → 组装批 → 交给「投递器」异步发送 → 清空缓冲（保留 overlap）。

## 7. 投递分析后端（占位接口契约）

代理 → 分析后端，HTTP `POST application/json`。**先用占位（mock）实现，契约固定，后续只换 URL。**

```
POST ${analysis.backend.url}            # 配置项，默认指向本地 mock /mock/analysis
Headers: Content-Type: application/json
         X-Session-Id: <sessionId>
         X-Batch-Id: <batchId>          # 幂等键，重试不重复处理
Body:
{
  "sessionId": "sess_xxx",
  "batchId": "b_uuid",
  "batchSeq": 3,
  "isFinal": false,                     // 是否会话最后一批
  "createdAt": "2026-06-02T10:00:00Z",
  "triggeredBy": "charThreshold",       // 命中的触发器，便于调参/排查
  "chars": 213,
  "context": [                          // 上一批末尾重叠句(可空)
    { "sentenceId": 11, "text": "……前文最后一句。" }
  ],
  "sentences": [                        // 本批定稿句，按时间有序
    { "sentenceId": 12, "beginTime": 12030, "endTime": 14200, "text": "……" },
    { "sentenceId": 13, "beginTime": 14200, "endTime": 17800, "text": "……" }
  ],
  "text": "拼接好的本批纯文本，方便直接用"
}
```
占位后端返回 `200 {"received": true}` 即可。

**投递可靠性**
- 失败重试：指数退避（1s/2s/4s/8s），最多 N 次；
- 本地队列：重试期间新批入内存队列（可选落盘），保证顺序与不丢；
- 幂等：靠 `X-Batch-Id`，下游/重试都安全；
- 投递与转写解耦：投递走独立线程池，不阻塞音频实时链路。

## 8. 稳定性设计

| 维度 | 措施 |
|---|---|
| 双链路重连 | ① 前端↔代理断线：前端指数退避自动重连，重连后用同 `sessionId` 续传；② 代理↔DashScope 断线：代理自动重建任务（新 `task_id`），期间前端音频短暂缓冲，无缝衔接 |
| 心跳保活 | `parameters.heartbeat=true` + 应用层 ping/pong，静音长时间也不被中间设备断开 |
| 会话时长上限 | DashScope 单任务有时长上限，代理在接近上限前**主动 finish + 重开新任务**（rolling session），对前端透明，避免被动断流丢内容 |
| 背压 | 前端发送速率按音频实时速率自然限速；代理出站缓冲设上限，超限丢「最旧的中间结果」而非最终句 |
| 限流/配额 | 代理侧对单 IP/单用户并发会话数限流；捕获 DashScope 限流错误码（如配额超限）并友好回传前端 |
| 错误分级 | 可重试错误（网络/限流）→ 自动重连/退避；致命错误（鉴权失败/参数错）→ 立即上报前端并停止，不空转 |
| 密钥保护 | `DASHSCOPE_API_KEY` 仅存代理环境变量，永不下发前端；代理对前端只暴露 `/ws/asr` |
| 资源回收 | 会话结束/超时/前端断开 → 关闭 DashScope WS、停定时器、flush 残余、释放线程，防泄漏 |
| 可观测 | 结构化日志（sessionId 串联全链路）、关键指标（首字延迟、句延迟、flush 批数、投递成功率、重连次数），便于上线后调参 |

## 11. 实施步骤（里程碑）

1. **M1 打通链路**：React 采集 16k PCM → 代理透传 DashScope → 实时结果回显（验证音频格式/协议正确）。
2. **M2 聚合投递**：实现 Aggregator + 占位后端，跑通「字数阈值」一种触发，端到端见到成批数据。
3. **M3 综合触发**：补齐时间/停顿/句数/兜底/结束强制 + overlap，配置化。
4. **M4 稳定性**：双链路重连、心跳、滚动会话、投递重试与本地队列、限流。
5. **M5 打磨**：日志指标、参数调优、异常文案、压测。

## 12. 关键风险与对策

| 风险 | 对策 |
|---|---|
| 浏览器音频不是 16k PCM，直接发会识别乱码 | AudioWorklet 严格重采样+Int16，M1 用已知音频回归验证 |
| 把内容按字数硬切导致半句/语义断裂 | 切批一律对齐 `sentence_end` 句界 + overlap 上下文 |
| 说太久 DashScope 任务超时断流丢内容 | 滚动会话主动重开 + 结束强制 flush 兜底 |
| 投递分析后端失败丢数据 | 幂等 batchId + 退避重试 + 本地队列 |
| API Key 泄露 | 仅存代理环境变量，前端零接触 |
| 官方字段/参数名细节差异 | 以官方 FUN-ASR WebSocket 文档为准，DashScopeClient 集中封装，改一处即可 |

> 注：DashScope 官方文档对部分地区 IP 有访问限制，落地前请以
> `help.aliyun.com/zh/model-studio/fun-asr-realtime-websocket-api` 的最新字段为准，
> 协议封装已集中在 `DashScopeClient`，字段微调成本低。
